Fix these before anything else

Not missing features — columns going out to customers today with content that is wrong.

P0 review_count

review_count carries the photo count

On the 53 places that appear in both files, BRG's review_count is exactly equal to Outscraper's photos_count on 49 of 53 — and equal to the real review count on zero. Nandhana Palace: BRG reports 2,121 reviews. Google has 10,470 reviews and 2,121 photos.

FixBind review_count to the review counter node and emit the photo counter as its own photos_count column. Both numbers are already being scraped — they are landing in one mislabelled column.
P0 description

description is a copy of the business name

All 785 of 785 rows have description identical to name. The column carries no information at all. Outscraper puts Google's editorial description there and leaves it blank when Google has none.

FixScrape the description block. Blank is the correct value when Google has none — Outscraper fills it on 18% of rows.

Only 53 places appear in both files. The two scrapers are not finding a similar list and missing a few of each other’s — they are exploring almost entirely different parts of Bangalore. Outscraper ran restaurant against ten separate Bangalore postal codes and merged the results. Expand the location into postal codes or a lat/lng grid, run one search per tile, then merge and de-duplicate on place_id. Done properly that should beat 1,000, not just match it.

The brief, in four lines

  1. Fix review_count. It holds the photo count. Emit the real review count, and add photos_count as its own column — we already scrape that number.
  2. Fix description. It is a copy of the name on all 785 rows.
  3. Add the 67 missing columns, in Outscraper’s exact order. Biggest wins by fill rate: about (89.7% — the whole attributes blob), the reviews_per_score histogram (93.9%), time_zone and h3 (99.8%, both computable from lat/lng we already have), kgmid, street_view, order_links (Swiggy/Zomato — high value on a restaurant list), and the contact block: full_name, title, contact_linkedin and email validation status.
  4. Tile the query. Ten postal-code searches instead of one city search is the whole 785-vs-1,000 gap.
